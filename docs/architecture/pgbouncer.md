# PgBouncer: Connection Pooling for AgentHive

**Proposal:** P499 — Stage A5 of P429 (Platform Scaling)  
**Status:** Implementation stage (AC-1..17)  
**Config template:** `config/pgbouncer/pgbouncer.ini`  
**Provisioning:** `scripts/pgbouncer/provision-pgbouncer.ts`  
**MCP ops tools:** `pgbouncer_stats`, `pgbouncer_ping`, `pgbouncer_reload`

---

## Overview

PgBouncer runs on loopback at port **6432** in **transaction mode**, pooling connections to:
- **Control-plane database** (`agenthive`)
- **Tenant databases** (per-project; rows in `roadmap.project`)

All **query-issuing clients** (application code, orchestrator, liaison agents) connect through PgBouncer at **6432** for automatic connection pooling and load balancing.

**CRITICAL:** Clients that issue `LISTEN` or `UNLISTEN` must bypass PgBouncer and connect directly to Postgres at **5432**. Transaction mode breaks LISTEN semantics.

---

## Architecture: Query vs. LISTEN Separation (Option A)

### Query Clients → PgBouncer (6432)
```
Application Layer
    ↓ (connect via :6432 via PGBOUNCER_HOST or AGENTHIVE_PG_PORT)
PgBouncer (transaction mode, port 6432)
    ↓ (multiplexes to)
PostgreSQL (port 5432)
```

Pool capacity:
- `default_pool_size = 20` connections per database
- `max_client_conn = 400` concurrent client connections
- `reserve_pool_size = 5` emergency overflow

### LISTEN Clients → Direct Postgres (5432)
```
LISTEN-issuing Code (feature-flag-service, state-names, orchestrator, websocket-server)
    ↓ (connect via PGPORT_DIRECT=5432 or AGENTHIVE_LISTEN_PORT)
PostgreSQL (port 5432, direct connection)
    ↓ (NOTIFY events received here)
Client
```

Affected channels:
- `pool_evict` — pool-registry.ts eviction signaling
- `runtime_config_changed` — feature-flag-service listener
- `feature_flag_changed` — feature-flag-service listener
- `control_feed` — pool watchdog events (P522)
- `agent_lifecycle_events` — pool watchdog and liaison state

### Key Sections

#### [databases]
Auto-generated by `scripts/pgbouncer/provision-pgbouncer.ts`:
```ini
agenthive = host=127.0.0.1 port=5432 dbname=agenthive

# Tenant databases (added at onboard time)
monkeyking-audio = host=127.0.0.1 port=5432 dbname=monkeyKing-audio

# Wildcard fallback (remove once all tenants are explicit)
* = host=127.0.0.1 port=5432
```

#### [pgbouncer]
- `listen_port = 6432` — PgBouncer endpoint (query clients)
- `pool_mode = transaction` — transaction pooling (required for LISTEN bypass)
- `default_pool_size = 20` — connections per database
- `max_client_conn = 400` — max concurrent clients
- `auth_type = scram-sha-256` — password hash type
- `auth_file = /etc/pgbouncer/userlist.txt` — user credentials

### Credentials: userlist.txt

PgBouncer reads SCRAM-SHA-256 password hashes from `userlist.txt`.

**Operator setup:**
```bash
# Extract hashes from pg_authid (one-time setup)
psql -c "\copy (SELECT concat('\"', rolname, '\" \"', rolpassword, '\"') 
           FROM pg_authid WHERE rolpassword IS NOT NULL) 
           TO '/etc/pgbouncer/userlist.txt'"

# Restart PgBouncer
sudo systemctl restart pgbouncer
```

## Environment Variables

### Query Pool Routing (Default: 6432 / PgBouncer)

| Env Var | Default | Purpose |
|---------|---------|---------|
| `PGHOST` | `127.0.0.1` | PgBouncer or Postgres host |
| `PGPORT` | `6432` | PgBouncer port (when P499 deployed) |
| `AGENTHIVE_PG_PORT` | `6432` | Explicit query-pool port override |
| `PGBOUNCER_HOST` | (unset) | Alternative PgBouncer hostname (if not 127.0.0.1) |

### LISTEN Bypass (Direct Postgres: 5432)

| Env Var | Default | Purpose |
|---------|---------|---------|
| `PGPORT_DIRECT` | `5432` | **Direct Postgres port** for LISTEN-only connections |
| `AGENTHIVE_LISTEN_PORT` | `5432` | Alias for `PGPORT_DIRECT` |

**Example backward-compatible startup:**
```bash
# Before P499: no PgBouncer, all clients use direct :5432
PGHOST=127.0.0.1 PGPORT=5432 npm start
# Result: no env vars set → pool.ts defaults to :5432, all clients connect direct

# After P499: query clients use bouncer, LISTEN clients use direct
PGHOST=127.0.0.1 AGENTHIVE_PG_PORT=6432 PGPORT_DIRECT=5432 npm start
# Result: query clients → :6432 (bouncer), LISTEN clients → :5432 (direct)
```

## Backward-Compatibility Guarantee

**Absent environment variables = unchanged behavior:**

| Scenario | Config | Behavior |
|----------|--------|----------|
| No P499 env set | `PGHOST=127.0.0.1` | All clients → `:5432` (direct Postgres) |
| P499 deployed | `AGENTHIVE_PG_PORT=6432` | Query → `:6432` (bouncer), LISTEN → `:5432` (direct) |
| Bouncer disabled (ops) | `PGPORT=5432` | All clients → `:5432` (direct Postgres) |
| Custom LISTEN port | `PGPORT_DIRECT=5433` | LISTEN clients → `:5433` |

See `src/infra/postgres/pool.ts` line 286–288 for port resolution logic.

## Provisioning

### First-Time Setup

```bash
# 1. Copy template to live path
sudo cp config/pgbouncer/pgbouncer.ini /etc/pgbouncer/pgbouncer.ini

# 2. Generate userlist.txt from Postgres
psql -c "\copy (SELECT concat('\"', rolname, '\" \"', rolpassword, '\"') 
           FROM pg_authid WHERE rolpassword IS NOT NULL) 
           TO '/etc/pgbouncer/userlist.txt'"
sudo chown pgbouncer:pgbouncer /etc/pgbouncer/userlist.txt
sudo chmod 600 /etc/pgbouncer/userlist.txt

# 3. Start PgBouncer
sudo systemctl start pgbouncer
sudo systemctl status pgbouncer
```

### Dynamic Re-provisioning (Add/Remove Tenants)

The provisioning script automatically regenerates `pgbouncer.ini` when tenants are onboarded:

```bash
# Run once at startup (with --watch for continuous re-provisioning)
sudo bun scripts/pgbouncer/provision-pgbouncer.ts --watch &
```

The script listens for `tenant_db_provisioned` NOTIFY events (triggered by `P508` when a new tenant is bootstrapped) and re-provisions PgBouncer within the 60-second SLA (AC-2).

**On provision failure:**
- Error logged to syslog
- Script exits; systemd restarts it via `Restart=on-failure`
- Manual recovery: `sudo bun scripts/pgbouncer/provision-pgbouncer.ts --dry-run` to test

## Troubleshooting

### All Connections Hung (Pool Exhausted)

**Symptoms:**
- New queries timeout
- `max_client_conn` saturation in `SHOW CLIENTS`
- No application errors, just silent hangs

**Diagnosis:**
```bash
# Check pool saturation
mcp_ops action="pgbouncer_stats"

# Manual admin check
psql -h 127.0.0.1 -p 6432 -d pgbouncer -U agenthive_admin -c "SHOW CLIENTS;"

# If cl_waiting > 10, pool is exhausted
```

**Resolution:**
1. Identify slow queries blocking connections: `SHOW SERVERS;`
2. Increase `default_pool_size` or `max_client_conn` in pgbouncer.ini (temporary, ops-managed)
3. Fix the application code causing connection leaks (permanent fix)

### LISTEN Not Receiving Notifications

**Symptoms:**
- LISTEN clients connect but don't receive `NOTIFY` events
- feature-flag-service stuck waiting for `feature_flag_changed`
- pool-registry.ts not reacting to `pool_evict`

**Root Cause:**
LISTEN client connected through PgBouncer (port 6432) instead of direct Postgres (port 5432).

**Check:**
```bash
# Verify environment variables on the failing service
ps aux | grep agenthive
# Look for PGPORT_DIRECT or AGENTHIVE_LISTEN_PORT
```

**Fix:**
Ensure LISTEN-issuing code uses:
```javascript
// pool-registry.ts, feature-flag-service.ts, state-names.ts
const port = Number(process.env.PGPORT_DIRECT ?? process.env.PGPORT ?? 5432);
// Must explicitly prefer PGPORT_DIRECT
```

Or set environment:
```bash
export PGPORT_DIRECT=5432
# Before starting the service
```

### PgBouncer Connection Refused

**Symptoms:**
```
error: connect ECONNREFUSED 127.0.0.1:6432
```

**Diagnosis:**
```bash
sudo systemctl status pgbouncer
sudo journalctl -u pgbouncer -n 50
```

**Fix:**
```bash
# Restart PgBouncer
sudo systemctl restart pgbouncer

# If config is invalid, test with --dry-run
sudo bun scripts/pgbouncer/provision-pgbouncer.ts --dry-run
```

### Auth Failures (SCRAM Mismatch)

**Symptoms:**
```
FATAL: invalid password for user "agenthive"
```

**Diagnosis:**
```bash
# userlist.txt must contain SCRAM hashes, not plaintext
sudo cat /etc/pgbouncer/userlist.txt

# Verify PgBouncer sees the correct hash
psql -h 127.0.0.1 -p 6432 -d pgbouncer -U agenthive_admin -c "SHOW CONFIG;" | grep auth
```

**Fix:**
Regenerate `userlist.txt` from Postgres `pg_authid`:
```bash
psql -c "\copy (SELECT concat('\"', rolname, '\" \"', rolpassword, '\"') 
           FROM pg_authid WHERE rolpassword IS NOT NULL) 
           TO '/etc/pgbouncer/userlist.txt'"
sudo chown pgbouncer:pgbouncer /etc/pgbouncer/userlist.txt
sudo chmod 600 /etc/pgbouncer/userlist.txt

# Reload
psql -h 127.0.0.1 -p 6432 -d pgbouncer -U agenthive_admin -c "RELOAD;"
```

## Performance Tuning

### Memory Usage

PgBouncer memory is proportional to:
```
Memory = (default_pool_size × num_databases × connection_overhead) + buffers
       ≈ (20 connections × 10 databases × 5KB) + 2MB
       ≈ 3MB for typical AgentHive setup
```

Monitor with:
```bash
ps aux | grep pgbouncer
```

### Query Latency Impact

Transaction-mode pooling introduces negligible overhead (<1ms per query) due to:
- Local loopback networking (127.0.0.1)
- Connection reuse (no TCP handshake per query)
- Prepared statements (no parse/bind overhead in app layer)

**Before P499:** All app connections directly compete for Postgres resources.  
**After P499:** PgBouncer multiplexes 400 client connections to 20 server connections per database.

### Timeout Tuning

Default timeouts in `pgbouncer.ini`:
- `server_connect_timeout = 15` — fail fast if Postgres is down
- `query_timeout = 0` — no per-query timeout (honor application logic)
- `query_wait_timeout = 120` — fail if client waits >2min for server

Adjust if your workload differs from AgentHive.

## Connection Budget Math (AC-20)

**Goal:** Ensure that Postgres `max_connections` is not exceeded when scaling tenants.

### Formula

With N tenant databases and 5 processes per tenant (liaison + worker × 4), the total Postgres connections required is:

```
Total Connections = 5 × (pool_size_hiveCentral + pool_size_agenthive + pool_size_per_tenant × N)
                  = 5 × (20 + 10 + 8 × N)
                  = 5 × (30 + 8N)
                  = 150 + 40N
```

Where:
- `5` = number of processes per tenant (1 liaison + 4 workers)
- `20` = `default_pool_size` for `hiveCentral` database (AC-7)
- `10` = `default_pool_size` for `agenthive` database (AC-7)
- `8` = `default_pool_size` per tenant database (AC-7)
- `N` = number of active tenant databases

### Capacity Planning

Postgres default `max_connections = 100`. Recommended overhead: `max_connections = 200`.

| N Tenants | Total Connections | Status | Postgres Limit |
|-----------|-------------------|--------|-----------------|
| 0 | 150 | ✅ Fits | 100+ |
| 1 | 190 | ✅ Fits | 100+ |
| 2 | 230 | ⚠️ Marginal | 200+ required |
| 3 | 270 | ❌ Exceeds 200 | 300+ required |
| 4 | 310 | ❌ Exceeds 200 | 400+ required |

### Operational Rules

1. **For N ≤ 2:** No action required. Default `max_connections = 100` is sufficient.

2. **For N = 3:** Increase Postgres `max_connections` to 300 before provisioning the 3rd tenant.
   ```bash
   # In /etc/postgresql/*/main/postgresql.conf
   max_connections = 300
   
   # Then reload:
   sudo systemctl reload postgresql
   ```

3. **For N ≥ 4:** Increase Postgres `max_connections` to `150 + 40N + 50` (50-connection safety margin).
   ```
   max_connections = 150 + 40N + 50 = 200 + 40N
   ```

4. **Monitoring:** Track active connections via:
   ```bash
   psql -c "SELECT count(*) FROM pg_stat_activity;"
   ```

### PgBouncer + Postgres: Connection Multiplexing

- **Without PgBouncer:** 400 concurrent app clients compete directly for ~100 Postgres connections (typical).
  - High overhead; pool exhaustion risk under load.

- **With PgBouncer (P499):** 400 app clients → PgBouncer → 20–40 Postgres connections.
  - Multiplexing ratio = 400 / 30 ≈ 13:1 (dramatic reduction).
  - Fits comfortably within `max_connections = 100–200`.

### Example: 2-Tenant Deployment

```
Tenant 1: monkeyKing-audio (5 processes)
  - Liaison + 4 workers = 5 connections to monkeyKing-audio DB
  - Plus 20 to hiveCentral + 10 to agenthive = 35 connections

Tenant 2: georgia-singer (5 processes)
  - Liaison + 4 workers = 5 connections to georgia-singer DB
  - Plus 20 to hiveCentral + 10 to agenthive = 35 connections

Total: 35 + 35 = 70 connections
Postgres max_connections = 100 (default sufficient)
```

### Scaling Beyond 4 Tenants

If your deployment needs N > 4 tenants, consider:

1. **Horizontal scaling:** Deploy a separate Postgres instance per tenant or tenant group.
2. **Connection pooling per tenant:** Run a separate PgBouncer instance per tenant (advanced).
3. **Application-level pooling:** Reuse connections more aggressively in application code.
4. **Increase Postgres limits:** Scale to `max_connections = 400–1000` on high-resource hardware.

## Migration Path (Zero-Downtime)

1. **Prepare:** Deploy P499 code without enabling PgBouncer
   - `PGPORT` still defaults to 5432 (direct Postgres)
   - All code paths tested with new routing logic

2. **Validate:** Smoke-test in staging with PgBouncer on localhost
   - Run `provision-pgbouncer.ts --dry-run`
   - Test query + LISTEN separately

3. **Deploy PgBouncer:** Start service, test connectivity
   ```bash
   sudo systemctl start pgbouncer
   mcp_ops action="pgbouncer_ping"
   ```

4. **Enable Routing:** Update `/etc/agenthive/env`
   ```bash
   AGENTHIVE_PG_PORT=6432      # query clients → bouncer
   PGPORT_DIRECT=5432          # LISTEN clients → direct
   ```

5. **Restart services:**
   ```bash
   sudo systemctl restart agenthive-mcp-server  # picks up new env
   sudo systemctl restart agenthive-orchestrator
   sudo systemctl restart agenthive-liaison@...
   ```

6. **Monitor:** Check pool stats for 24 hours
   ```bash
   watch -n 5 'mcp_ops action="pgbouncer_stats" | jq .pools'
   ```

7. **Rollback (if needed):**
   ```bash
   # Restore PGPORT=5432 in /etc/agenthive/env
   # Restart services
   # PgBouncer can run alongside (no conflicts)
   ```

## Glossary

- **Transaction mode:** PgBouncer automatically returns a server connection to the pool after each transaction (COMMIT/ROLLBACK). Enables N clients to share M server connections.
- **Statement mode:** PgBouncer returns connections after each statement. Breaks applications that rely on session state (cursors, prepared statements).
- **LISTEN:** Postgres-specific notification mechanism (not compatible with transaction-mode pooling without a direct connection).
- **Pool exhaustion:** All available server connections in use; new client requests wait in queue.
- **Pool eviction:** Removing a tenant from the pool registry due to schema drift or connectivity loss.
- **Bypasss:** Direct connection to Postgres, avoiding PgBouncer.
